# RAW 双路径与批量试片

当前缓存和两阶段开发的约束见 [图像缓存与 RAW 两阶段开发](photo-cache.zh-CN.md)。
本文末尾的旧测速保留为历史记录，不代表当前一次解码双输出的耗时。

RAW 只走两条输入路径，共用 RawTherapee 的相机配置和 AsShot 白平衡：

1. **原图**：RAW → RawTherapee → sRGB D65。A 与胶片配方无关，不经过 OpenDRT。
2. **胶片输入**：RAW → RawTherapee → 线性 ACEScg（AP1／D60）；应用导出的 LUT 时，再编码为 ACEScct（AP1／D60）。不经过展示用的 sRGB 文件。

普通 Bayer 当前使用仓库内集成构建的 RawTherapee 5.12，源码标签对应
[`a8a3d1bc`](https://github.com/RawTherapee/RawTherapee/tree/a8a3d1bc7b419ed1c974c39276c97e618a4f9a1b)。
同一阶段只调用一次 CLI，复用校正后的 RT Lab 生成两路 ICC 输出；预览和完整开发分别保留。
Bayer 预览使用四像元读取，完整解拜耳延迟到导出。输出为 32 位浮点 RGB TIFF，
逐一核对类型、尺寸、有限值和内嵌 ICC。线性 AP1 的 ICC 由本项目按标准色度定义
生成，TRC 为 1，不把 RawTherapee 的工作空间选择当作导出文件编码的证据。

可用相机白平衡缺失时，保留 RawTherapee 的回退，并在输入记录及胶片条旁明确标出。

CLI 从中性参数开始，只加载应用 PP3，不使用 `-d`、`-s`、`-S` 或快速导出。
设置目录隔离，避免用户偏好和旁车文件覆盖输入。`cameraICC` 自动选择匹配的
内置 DCP，其次 ICC，再回退相机矩阵；这是 RawTherapee 的策略，不代表每款相机
已通过本项目实拍校准。DCP HueSatMap 和基线曝光保持启用，LookTable、ToneCurve
关闭。曝光补偿为 0，锐化、降噪、局部色调和缩放关闭。完整导出的 Bayer 使用 AMaZE，
X-Trans 使用三遍算法。Bayer 预览从已校正的 CFA 取 R、平均两颗 G、B，
不经过解拜耳；其他传感器或非标准几何保留 RT 读取。X-Trans 当前使用保留的官方 5.12 CLI，
不启用新引擎的四像元路径。胶片曝光与照片输入曝光在交接之后分别处理。
当前没有自定义 DCP 和白平衡编辑界面。

试片 B 沿用连续胶片参考计算，消费线性 ACEScg。导出的 CUBE 消费 ACEScct，
两者不是不同的色域。后端同时给出选点的实际 ACEScct 坐标。ACEScct 编码前不
裁切负值或超过 1 的值；这不保证 RawTherapee 之前的传感器、DCP 或色彩处理
完全没有裁切。不要用本次测试声称整条 RAW 管线无限保留 HDR。

## 批量操作

试片顶部的「导入照片…」可一次选择多张 RAW、PNG 或 JPEG。底部胶片条横向
滚动，点击或用左右方向键切换。每张照片保存自己的输入曝光，配方由整组共用。
重复文件按内容去重；一张损坏文件不阻断其他照片。工作区保存照片顺序、选中项
和逐张曝光；重新打开时恢复。

「批量导出…」冻结当前配方和各张输入曝光，逐张输出原尺寸 PNG。显示实际完成
数量，可停止等待中的后续照片；正在计算的一张会先完成。关闭进度窗口不停止
任务，可再次点击批量导出查看。成功图像、配方和简短清单放在 ZIP 中；部分失败
仍可下载成功图像。像素和输出 ICC 逐张读回校验。当前文件输出为 8 位 sRGB、
Display P3 或 Rec.1886，内部 RAW 交接保持浮点，不声称提供浮点照片导出。

限制：每个工作区最多 512 张；PNG／JPEG 每张 16 MiB、1200 万像素；RAW 每张
256 MiB、6400 万像素。相机文件是否可开发取决于所用 RawTherapee 的支持。
过大或不支持的文件会明确报错，不用内嵌 JPEG 冒充 RAW 开发。

## 缓存与任务

参考用户指定的 [AlcedoStudio](https://github.com/zidage/AlcedoStudio/tree/18c863702565e4be7cba5d889314b555b6fb6037)
的缩略图服务、磁盘缓存和导出队列，沿用本项目的 AppKit／WebKit 外壳与 C++
计算内核。没有搬入 Qt／GPU／数据库框架，也没有导入其源代码。

- 原照片、RAW 开发结果、预览数组和胶片条缩略图分别保存。胶片条使用 112×80
  以内的缩略图，预览在读取后短边超过 2048 时缩小，导出使用原尺寸。
- 已校验的预览从磁盘按需读取，解码数组使用 512 MiB LRU；启动不重新解码所有照片。
- RAW 开发结果以原文件、CLI、相机配置数据库、PP3 和输出 ICC 的哈希为键。
  损坏的 RAW 开发数据报错，不静默再次开发；显示成片缓存可由浮点数据恢复。
  RAW half/full 数据、原照片和配方不属于可自动清理缓存。
- 导出使用一个后台 worker，最多保留 4 个等待／执行任务。RAW 开发限制为一对
  输出顺序执行；排队中的交互读取优先于后台导出，已经开始的一对不会中断。
  同一 RAW 的并发未命中在取得解码名额后再次查缓存，避免重复开发。
  预览合并待处理调整，并使用请求序号拒绝旧结果。
- RAW TIFF 使用只读内存映射；导出只映射 AP1 分支。原件和 TIFF 第一次完整流式
  校验；应用拥有的不可变开发数据按文件身份复用进程内校验记录，避免每次切图重读。
  这一进程内记录有数量上限，重启后重新校验；不会跳过配置或像素完整性检查。
  缓存按实际访问淘汰，清理不删除原件。
- 第一张导入完成后立即显示，其余继续导入；用户中途选了其他照片就保留该选择。
  试片模式不触发隐藏的色卡诊断。
- 暂无区域渲染、可恢复导出任务或大图库数据库。退出时等待导入／
  导出结束或主动停止，避免将运行中的任务当作已保存工作。

当前默认使用 `third_party/rawtherapee` 的固定源码与官方资源，通过根 CMake
构建 `RawTherapeeEngine.app`。X-Trans 的兼容路径仍需保留经过核验的官方 CLI
及其公开资源；没有兼容读取器时明确报错。构建依赖公开
库仍来自本机开发环境，尚不是独立分发安装包。完整输出和预览可分别使用
`SOFTLOAF_RAWTHERAPEE` 与 `SOFTLOAF_RAWTHERAPEE_PREVIEW` 指定开发入口。

## 验证范围

运行 `python -m experiments.validate_raw_handoff`，读取已有的 R5、D850 合成 DNG。
用独立 colour-science AP1→XYZ、Bradford 和 IEC sRGB 公式检查 RawTherapee 两条输出
之间的颜色关系，同时检查 ACEScct 公式。报告在 `artifacts/raw-handoff-review/report.json`。
两个文件的逐像素最大通道误差，P99 分别为 0.0296／0.0309 个 8 位码值，最大 0.0424／0.0460；全部在 2/255 内。ACEScct 与独立分段公式一致。这证明本次交接及编码，不证明真实相机的配置准确度，也不改变胶片材料／RGB 近似
的既有误差结论。

自动测试另覆盖：缓存命中与损坏重建、重启免解码、独立原图分支、逐张曝光、任务
快照、取消、部分失败、ZIP／像素／ICC 读回。界面实测通过文件选择器导入两张 PNG、
一张合成 DNG 和一张损坏文件，三张成功并完成批量导出；重载恢复顺序和曝光。

实拍补充测试见 [23 份相机 RAW 验证](real-camera-raw-verification.zh-CN.md)，其中记录了格式遗漏与清缓存后原件重建问题及修正。

## 2026-10-28 读取效率检查

同一 Canon EOS R6 RAW（RawTherapee 输出 3396 × 2262）在这台 M2 Pro 上五次
缓存命中的中位交接时间，由旧路径约 125 ms 降至 2.3 ms；只请求 AP1 的导出
交接约 1.1 ms。第一次校验约 137 ms。避免每次分配两张总计 176 MiB 的 RGB
数组；映射页仍会随实际计算进入内存，并非 RAW 零内存。结果逐项像素相同。
报告在 `artifacts/metal-preview/raw-cache-verification.json`。这些数字来自迁移到 T7 之前的内置盘，不能套用到当前每次重验哈希的外置盘路径。
只计命中缓存
的读取交接，不包含后续页访问、缩放、Metal、PNG 或首次 RAW 解码。

Alcedo 参考版本仍为 `18c86370`，本次补读 `raw_input_loader.cpp`：它使用分辨率
档位在 CFA 阶段缩小，并由独立解码 worker 向渲染阶段交接。我们采用分离调度、
按需缓存与有界解码原则，未复制其代码或更换 RawTherapee。上面的缓存测试记录的是改动前的完整解拜耳路径。随后已集成 RT 源码，
把 Bayer 导入改为预览专用的四像元读取，完整开发留到导出。四像元预览和
完整解拜耳在细节、噪声和少数边缘颜色上会不同，未称作逐像素等价。

## 四像元预览与源码集成

Issue #9，2026-10-28。RT 源码、LibRaw、相机数据库和原有许可证保留在
`third_party/rawtherapee`；集成改动与原始版本记录见
[RAW 模块说明](../third_party/rawtherapee/SoftLoaf.md)。根 CMake 自动构建 CLI。

预览读出的短边超过 2048 px 时才等比缩小，否则保持读取尺寸；不放大。
例如 R6 文件原尺寸 3396×2262，四像元后 1698×1131，保留该尺寸；D850
原尺寸 8280×5512，四像元后 4140×2756，再缩至 3076×2048。竖幅同样
按方向处理。原图文件和原尺寸记录始终保留，导出重新完整开发。

普通 Bayer 的 R/G/B 来自同一个 2×2 单元，两个已校正的绿色取平均。CFA
布局由实际滤色阵列决定；单色、四色、Super-CCD、D1X、X-Trans 等没有被
强行当作普通 Bayer。原生 LibRaw `half_size=1` 与 `raw2image()` 已独立验证，
但它不改变 RT 消费的 `rawdata.raw_image`；RT 只在原始数据出口增加很小的
浮点衔接，保留其黑电平、白平衡、DCP/ICC 与相机色彩处理。

使用可重入 `libraw_r.a`，同时明确启用 RT 和 LibRaw 的 OpenMP。应用一次
只放行一对昂贵的 RAW 输出，每个 CLI 最多四线程，关闭嵌套线程组；后台
导出不抢在等待中的当前照片之前。多核效果取决于解码器，`_r` 本身不是
所有解码器自动并行的保证。旧预览按需升级，不在启动时批量完整开发。

运行 `python -m experiments.verify_raw_superpixel --raw-root <已授权的相机目录>`
会以独立的新缓存比较
CR3、NEF、RAF 和竖幅文件，检查原尺寸、缩放策略、独立色度桥接及面积平均
后的预览/完整输出差异。测试记录在 `artifacts/raw-superpixel-integrated/`，
相机原件、结果图像和第三方资料未随源码发布。

## 同工作空间与兼容读取

完整输出另与原官方 5.12 CLI 的结果比较，固定相同原件、技术 PP3、AsShot
白平衡、相机配置和图像尺寸，分别比较线性 ACEScg（AP1／D60、float32）与
编码 sRGB（D65、float32）。R6、D850 与竖幅 Nikon 1 S2 的独立引擎对照中，
AP1 最大差为 0，sRGB 最大差不超过 1.2e-6；这不是只比较新引擎内部两条路径。

X-T30 II 的候选引擎在最底部少数 AP1 像素仍出现约 0.02 的差异，限制线程数
没有稳定消除它，原因尚未确定。因此 X-Trans 继续走原官方 RT 5.12 兼容读取，
不把候选结果当作已通过。当前兼容读取只开发一次 AP1，再由实际 ICC 通过
LCMS2 浮点相对色度转换生成 sRGB；独立基准最大差为 2.3842e-7。通过 LibRaw 的传感器元数据识别 X-Trans，不按 RAF
扩展名猜测。交接记录实际引擎哈希、读取方式和回退原因。四像元预览与完整
解拜耳另记空间重建差异，不要求逐像素相同；这些相机样本也不证明所有机型
或 DCP 的色彩准确度。

`experiments/compare_raw_engines.py` 校验缓存文件哈希，按同一输入内容匹配，
分块比较 AP1 与 sRGB，超出阈值时先保存报告再失败。候选 X-Trans 的失败记录
保留，实际分流后的复核记录位于 `artifacts/raw-superpixel-final/dispatch-*/`。

RAW 原件、缓存、临时开发与高光谱数据现存放在 T7；见
[外置数据存储](external-data-storage.zh-CN.md)。配方工作区和普通检查报告仍在项目。

## 历史：缓存改造前与原官方 RT CLI 的速度对照

2026-10-28，在 Apple M2 Pro 和当前 T7 存储配置下，用原官方 RT 5.12 CLI
对照当前集成引擎的实际预览策略。每份输入各测三轮，交替执行顺序，表内为
中位数。每轮使用新的开发缓存；原件的操作系统文件页可能已缓存，因此不是
冷盘测试。所有 RAW、TIFF、缓存和临时开发仍在 T7。

计时包含两次 RT 输出（sRGB D65 与线性 ACEScg AP1/D60、float32 TIFF）、
当前外置盘完整哈希校验和两路预览缩放；不包含文件上传/原件复制、缩略图、
Metal、PNG 编码与界面显示。命中缓存列同样包含校验和缩放，并非界面切图延迟。
引擎构造在计时前完成。Bayer 请求四线程，X-Trans 两组均请求两线程。

| 测试文件 | 原官方 RT，无开发缓存 | 当前策略，无开发缓存 | 加速比 | 命中开发缓存，旧 → 新 |
| --- | ---: | ---: | ---: | ---: |
| Canon EOS R6（裁切测试文件） | 7.00 s | 1.97 s | 3.55× | 0.293 → 0.060 s |
| Nikon D850 | 40.77 s | 9.78 s | 4.17× | 1.224 → 0.444 s |
| Fujifilm X-T30 II | 23.03 s | 25.53 s | 慢约 11% | 0.723 → 0.753 s |
| Nikon 1 S2（竖幅） | 11.80 s | 3.41 s | 3.46× | 0.464 → 0.103 s |

Bayer 对照是完整 AMaZE 开发后缩小与四像元预览的比较，空间重建方法不同。
R6 新预览保留 1698×1131；旧完整输出缩至 3075×2048。D850 两边最终均为
3076×2048。结果说明实际预览策略的收益，不是同分辨率、同算法下对 LibRaw
或多核单项优化的独立计量，也不能作为完整导出加速比。

X-Trans 两边实际调用同一个官方兼容引擎，没有四像元路径；本轮新策略的
中位数反而慢约 11%，不能称为已加速。D850 无开发缓存耗时有波动：官方
33.68–46.35 s，新策略 7.66–11.84 s；这些数字仅代表本机和本组文件。
该轮测试时两路色彩交接仍分别调用一次 CLI。当前已经合并解码，
新的结构、切图数据和验证边界见缓存文档；不能把旧测速当作当前性能。

原始三轮记录、实际引擎身份与测速脚本保存在
`artifacts/raw-superpixel-final/t7-speed/5ac4247813634158874659bf1099efdf/`。
已核对每个缓存清单与对应原件内容哈希，全部数据缓存的解析路径都位于 T7。
